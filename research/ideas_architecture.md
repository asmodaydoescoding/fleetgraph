## 1. Delegation Contracts with Downward-Split Schema

**Concept.** Today the `delegate` frame is a free-form instruction sent from an orchestrator to one bot, and that bot is expected to "split work downward itself per the initiative ladder" (README § Message composer). That's a semantic expectation with no structural enforcement. Add a `delegate_contract` payload to the `POST /send` path and to `fleet_msg.py` that carries (a) a task spec, (b) a maximum delegation depth, (c) an optional per-hop capability constraint, and (d) a completion-signal schema the receiving bot must return when it has finished decomposing and delegated. The graph layer gains a `can_delegate_to(graph, sender, recipient, contract)` check that walks the chain of command and refuses contracts whose declared depth exceeds the available subordinate tree below `recipient`. This turns delegation from a hope into a verified routing decision.

**Files touched.** `fleet_graph_core.py` (new `can_delegate_to` + depth/feasible-subtree helper), `dashboard/plugin_api.py` (`POST /send` body extension + validation before enqueue), `fleet_msg.py` (contract schema on the CLI side so bot-launched delegations use the same envelope), and the desktop composer in `desktop-plugins/fleet-graph/plugin.js` (delegate tab gains depth/capability fields and a feasibility preview against the live graph).

**Why it matters.** Delegation is the whole point of a hierarchical fleet — the initiative ladder explicitly hands work down — but right now the operator can't tell from the graph whether a bot actually *can* absorb a delegation into its subtree without inventing ad-hoc sub-bots or silently failing. A contract schema plus a graph-side feasibility check closes that gap, gives the desktop a live "this delegation will reach N bots under X" preview, and makes the bot-side "split work downward" prompt legible to the operator instead of opaque. SPOQ's specialist-queuing idea and BOHM's hierarchical-attribution thinking both point here: orchestration is only as good as the structure that constrains it.

## 2. Semantic Information-Flow Policy Layer (SafeFlow-style)

**Concept.** FleetGraph already blocks lateral sends unless a peer relation exists (`can_communicate`), but the policy is purely structural: "are these two nodes connected by a supervisor/subordinate edge or a declared peer edge?" Add a second policy dimension that classifies each message by a small semantic tag set (e.g. `data`, `instruction`, `status`, `escalation`, `delegate`) and lets the operator declare per-edge or per-relation flow rules — "peers can exchange `status` and `data` but not `instruction` or `delegate`", "subordinates can send `escalation` upward freely but `delegate` only when the supervisor is the recipient", etc. The check lives alongside `can_communicate` as `can_communicate_with_policy(graph, relations, sender, recipient, frame, payload_tag)` and the `POST /send` validator applies it before enqueue. The desktop's Configure tab gains a per-relation policy editor (a small matrix of frame × allowed tags), and `/overview` can surface the effective policy on each edge as part of the paint payload. This is the SafeFlow insight applied at fleet scale: the graph is not enough, you also want to know *what kinds of things* are allowed to flow across each edge.

**Files touched.** `fleet_graph_core.py` (policy check function, policy normalization/validation on PUT, optional policy storage under `_meta` alongside relations), `dashboard/plugin_api.py` (`POST /send` policy enforcement + new `GET /policy` or policy embedded in `/overview`), `fleet_msg.py` (tag extraction from frame + payload so CLI-launched messages carry the same tag), and `desktop-plugins/fleet-graph/plugin.js` (Configure-tab policy matrix editor, edge policy shown in the graph tooltip / inspector).

**Why it matters.** The current policy is all-or-nothing per edge — a peer relation lets two bots send anything to each other, including instructions and delegations that the operator might want to keep on the supervised path. Real fleets develop informal norms (status updates fly sideways, delegations stay supervised, escalations go up) and encoding those norms as a first-class, graph-aware policy is the difference between "the graph says they're connected" and "the graph says they're connected *and* only these message types are allowed." SafeFlow's semantic information-flow framing is the right mental model: propagation control is about what, not just who.

## 3. Hierarchical Attribution + Delegation Ledger

**Concept.** When a bot delegates downward and that bot delegates further, the original requestor has no structural visibility into what happened beneath it — the initiative ladder says "report done" but doesn't give the operator a traceable attribution chain. Add a lightweight delegation ledger: each `delegate` message optionally carries a `trace_id` (set by the sender or auto-generated) and a `parent_trace_id`; bots that further delegate propagate both; when a bot reports completion it returns the trace chain. The graph plugin exposes two new surfaces: (a) a per-bot "active delegations" panel in the inspector showing open trace chains with depth and current holder, and (b) an `/attribution` endpoint (or an enrichment on `/overview`) that rolls up completed delegation work to the original requestor so the operator can see, for a given bot, what fraction of its reported-done work originated as its own task vs. something delegated down to it. BOHM's hierarchical attribution ("whose contribution is this, at which level?") and AGENTSERVESIM's multi-turn serving-trace thinking both motivate this: without attribution, a hierarchy is just a shape, not an accountable org chart.

**Files touched.** `fleet_msg.py` (trace envelope on delegate messages + completion reply semantics), `dashboard/plugin_api.py` (`POST /send` trace propagation, new `GET /attribution` or enrichment on existing endpoints, inbox watermark interaction so completed traces don't keep re-lighting badges), `fleet_graph_core.py` (optional: a helper that, given a trace chain and the graph, validates the chain is a valid downward path — catching forged delegation traces that jump sideways or upward), and `desktop-plugins/fleet-graph/plugin.js` (active-delegations panel in the inspector + attribution summary chip on each bot card / node).

**Why it matters.** Right now the operator sees each bot's inbox and transcript in isolation; there's no structural answer to "who asked for this, and how far did it travel?" A delegation ledger turns the graph from a static org chart into an accountable one — the operator can see where work originated, how deep it went, and which bots are acting as pure relays vs. actual doers. That's the difference between a fleet that *looks* hierarchical and one that *behaves* hierarchically under observation. It also gives the operator a concrete hook for the deferred "profile deletion should prune inboxes" decision, because delegation traces are exactly the kind of inbox content whose provenance matters when you consider pruning.
